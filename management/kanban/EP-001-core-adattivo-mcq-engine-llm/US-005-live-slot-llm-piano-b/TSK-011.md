# TSK-011 — Offline test: rete fisica staccata, flusso completo (buffer 3:30-4:00)

## Context

Parte di US-005 (Live slot LLM e Piano B). Il test offline è NON NEGOZIABILE: va eseguito nel buffer 3:30-4:00, prima di dichiarare la demo pronta. Se qualcosa crasha con rete staccata, il problema si risolve qui — non durante la demo. Questo test verifica che il Piano B (DEMO_MODE + Tier 3 fallback) funzioni in modo deterministico senza connessione.

[^src: management/kanban/EP-001-core-adattivo-mcq-engine-llm/US-005-live-slot-llm-piano-b/US-005.md §Business Rules]

## Technical Specs

> **Automatizzato integralmente (2026-09-14).** `node app/tests/offline-browser.mjs` esegue in Chromium i tre scenari in severita' crescente: (1) wifi staccato con proxy locale vivo — flusso L1 completo fino al report docente; (2) `DEMO_MODE=false` con `/complete` irraggiungibile — il live slot viene realmente tentato e degrada al Tier 3 in 37 ms; (3) offline totale, proxy compreso — la pagina resta usabile. Zero eccezioni non gestite. Tutta la DoD qui sotto e' coperta.
>
> Differenza residua rispetto allo scacco fisico del wifi: nessuna che tocchi una pagina statica locale — la fase 3 e' anzi piu' severa del reale, perche' spegne anche il loopback. Il passaggio a rete fisicamente staccata resta comunque dentro **TSK-024**, che non e' negoziabile.
>
> **Precedente nota parziale.** `node app/tests/offline-check.mjs` verifica senza staccare la rete: assenza di risorse esterne caricate da `<script>`/`<link>` (rischio CDN), flusso completo L1 fino al report con ogni `fetch` esterna che lancia, e degrado del live slot entro pochi ms invece di uno spinner infinito. **PASS.** Resta umano il dry run a rete fisicamente staccata.

- **Scenario:** WiFi off (o cavo Ethernet staccato fisicamente), browser già caricato con app aperta. Il proxy non è raggiungibile.
- **DEMO_MODE=true:** la chiave trovata in fixtures → mostra testo da fixtures (zero rete, funziona)
- **DEMO_MODE=true chiave non trovata:** mostra fallback testuale pre-scritto entro 2s senza spinner infinito (zero rete, funziona)
- **DEMO_MODE=false chiave non trovata → rete staccata:** il fetch al proxy fallisce → Tier 3 fallback mostrato entro 3s senza crash, senza spinner bloccato. Questo scenario va testato esplicitamente.
- **Flusso completo da testare:** seleziona L1 → step1 errore → remediation da fixtures (Tier1) → Riprova → avanza → step2 (transfer) → risposta → OutcomeTracker → report docente visibile
- **Fix critici:** se qualcosa crasha, identificare la causa, fixare, ri-eseguire test.

## Implementation Steps

1. Assicurarsi che il browser sia già aperto con l'app caricata e fixtures.json in memoria.
2. Staccare fisicamente il WiFi (o impostare "Offline" in DevTools → Network → Throttling).
3. Eseguire flusso completo con DEMO_MODE=true: L1 → errore denominator_magnitude → remediation da fixtures → Riprova → avanza → step transfer → risposta → report docente.
4. Verificare zero errori di rete visibili all'utente (nessun "Failed to fetch", nessuno spinner bloccato).
5. Testare caso DEMO_MODE=false con chiave non in fixtures + rete off: impostare `DEMO_MODE=false` in console → selezionare distractor non in fixtures → verificare Tier 3 fallback entro 3s.
6. Ripristinare DEMO_MODE=true dopo il test.
7. Riconnettere la rete.
8. Se ci sono stati crash: fixare e ripetere dalla step 2.

## Definition of Done

- [ ] Flusso completo L1 (errore → remediation → riprova → avanza → transfer → report) completato con rete off senza errori visibili
- [ ] Il fallback Tier 3 appare entro 3s con rete off e DEMO_MODE=false (nessuno spinner bloccato)
- [ ] Nessun crash JavaScript con rete staccata (DevTools console: zero uncaught exceptions)
- [ ] DEMO_MODE=true ripristinato dopo il test
- [ ] Eventuale fix applicato e test ri-eseguito con successo
